# Hack This Site — Basic Mission 7

## Overview

**Objective:** Find the password stored in an obscurely named file in the same directory as a script that executes the Unix `cal` command.

**Vulnerability:** OS Command Injection

**Status:** Completed

## 1. Initial Reconnaissance

The mission description mentioned two important details:

- The password was stored in an unencrypted file with an obscure filename.
- A script returned the output of the Unix `cal` command.

These clues suggested that inspecting the script's input handling and behavior could reveal a way to enumerate files in the current directory.

## 2. Inspecting the Request

Using the browser's Developer Tools, I inspected the form and its network request.

The relevant HTML was:

```html
<form action="/missions/basic/7/cal.pl" method="post">
    <input type="text" name="cal" />
    <input type="submit" value="view" />
</form>
```

### Observations

- **Endpoint:** `/missions/basic/7/cal.pl`
- **HTTP method:** `POST`
- **Input parameter:** `cal`
- **Expected behavior:** Return a calendar generated by the Unix `cal` command.

The request payload contained the submitted value under the `cal` parameter.

The `.pl` extension suggested that the endpoint might be implemented in Perl, although the extension alone did not confirm the server-side implementation.

## 3. Behavioral Testing

I tested several inputs to understand how the script responded:

| Input | Observed result |
|---|---|
| `1993` | Displayed the calendar for 1993 |
| Empty input | Displayed the current month's calendar |
| `sam` | Returned an empty response with HTTP status `200` |
| `1993; echo TESTE` | Displayed the calendar, but did not display `TESTE` |
| `1993 && ls` | Displayed the calendar followed by a directory listing |

The final test was the key observation.

The output of `ls` appeared after the calendar, demonstrating that the input could influence the execution of an additional command in the challenge environment.

This confirmed the command injection behavior in the context of the mission.

## 4. Enumerating the Directory

The directory listing revealed the following entries:

```text
index.php
level7.php
cal.pl
.
..
k1kh31b1n55h.php
```

The unusually named PHP file was a strong candidate for the password file described in the mission.

I accessed the file through the challenge environment and retrieved the password.

## 5. Result

The password was successfully retrieved and submitted through the mission's password form.

**Outcome:** Mission completed.

The challenge confirmed that improperly handling user-controlled input when constructing system commands can allow unintended command execution.

## 6. Security Analysis

### Root Cause

The observed behavior was consistent with user-controlled input being interpreted as part of a shell command without adequate protection against shell metacharacters.

The exact server-side source code was not available for inspection, so the underlying implementation details were inferred from the observed behavior rather than directly verified.

### Potential Impact

Depending on the privileges of the affected process and the server's configuration, OS command injection may allow an attacker to:

- Enumerate files and directories.
- Read files accessible to the application process.
- Access sensitive information, including credentials.
- Execute additional commands with the application's privileges.

### Recommended Mitigations

1. **Avoid shell execution when possible.** Use language-native functionality instead of constructing shell commands from user input.
2. **Use safe process-execution APIs.** If an external command is necessary, pass arguments separately without invoking a shell.
3. **Validate input.** Accept only the expected data type and range, such as a valid calendar year.
4. **Apply least privilege.** Ensure the application process cannot read or modify files it does not need.
5. **Protect sensitive files.** Store secrets outside publicly accessible web directories and enforce appropriate file permissions.
6. **Test server-side input handling.** Client-side form restrictions alone are not a security boundary.

## 7. Key Takeaways

- Browser Developer Tools can help trace user input from an HTML form to a server endpoint.
- An HTTP `200` response does not guarantee that an operation succeeded as intended.
- Behavioral testing can reveal server-side issues even when the source code is unavailable.
- Shell metacharacters have different meanings: `|` pipes output between commands, `;` separates commands, and `&&` runs the next command only if the preceding command succeeds.
- A directory listing can reveal sensitive files that were not linked from the web page.
- Observations and inferred implementation details should be documented separately.
